Executive Summary

Project at a Glance

Vortex combines a student job portal with an evidence-based career-readiness workspace. Students can discover opportunities, apply for jobs, upload a resume, connect optional GitHub and LeetCode evidence, inspect extracted skills, compare their profile against a selected role, and follow a personalized study roadmap. Placement administrators can manage job openings, review candidate evidence, and move applications through a structured pipeline.

The system is designed around a practical problem: a student may know the technologies listed on a job description but still lack a clear answer to three questions: which skills are actually demonstrated, which requirements remain weak, and what should be learned first. Vortex answers these questions through a controlled pipeline that combines text AI, embeddings, a curated role ontology, deterministic scoring, verified resources, and a grounded assistant.

1 / Foundation

Introduction and Problem Definition

1.1 Background

Campus placement systems commonly separate opportunity discovery from preparation. A student may find a job posting, submit an application, and receive a status update, but the system often does not explain how the student's demonstrated profile compares with the role requirements. This creates a gap between applying and improving.

Vortex closes this gap by combining job discovery, application tracking, profile evidence, role-specific analytics, and preparation guidance in one authenticated workspace. It is intended for students, placement teams, and academic demonstrations where explainability and secure ownership are important.

1.2 Problem Statement

Problem: students need an understandable and actionable method to assess their readiness for a target job, while placement administrators need a controlled way to manage openings and review candidates without exposing private profile data.

1.3 Proposed Solution

Vortex accepts a resume and optional public coding profiles, extracts structured skills with supporting evidence, validates and normalizes those skills, compares them against a curated target-role ontology, calculates readiness categories, and produces a prioritized roadmap backed by verified learning resources. The same platform supports job search, wishlist, applications, notifications, and administrator review.

1.4 Design Principles

Evidence before claims

Extracted skills carry source and evidence excerpts. Confidence is derived by application rules rather than blindly accepted from the model.

Server-side ownership

User identity, applicant ownership, report access, and administrator permissions are derived from verified JWT claims and backend middleware.

Deterministic decision layer

AI helps structure and explain information, while scoring, thresholds, priorities, and resource selection remain controlled by application code.

Actionable output

The final result is not only a number. It includes gaps, priorities, learning resources, practice suggestions, and a completion state.

6.3 Security Controls

  • Passwords are stored using bcrypt hashes and never returned.
  • JWT secrets, MongoDB credentials, Groq keys, Gemini keys, and GitHub tokens remain in server environment variables.
  • Resume files require PDF magic bytes, are size-limited, and are stored outside the public frontend.
  • Resume text is sensitive: it is not returned by profile APIs and is not written to logs.
  • Student ownership is checked for profiles, reports, applications, wishlists, and notifications.
  • Rate limits protect authentication, analysis, and the general API.
  • Validation rejects unknown or malformed fields before domain logic.

8.3 Structured Skill Record

Each extracted skill is stored with a display name, category, source list, evidence excerpts, and proficiency signals. The application merges casing duplicates and derives confidence using fixed rules: high confidence requires evidence from multiple sources, medium confidence requires one source with evidence, and low confidence represents a weak or bare mention.

{ "name": "React", "category": "frontend_framework", "sources": ["resume", "github"], "evidence": [{ "source": "resume", "text": "Built a dashboard using React" }], "proficiency_signals": { "projects_count": 2, "has_production_usage": true, "mentions_depth": "high" }, "confidence": "high" }
Important matching rule: related-looking technologies are not automatically interchangeable. React does not prove PyTorch; JavaScript does not prove Python; Node.js does not prove Machine Learning; UI/UX does not automatically prove frontend engineering. Upload validation also screens PDFs for resume signals before AI runs.

9 / Analytics

Analytics, Matching, and Scoring Engine

9.1 Role Ontology

The ontology is the controlled definition of role expectations. Each skill includes a canonical name, category, embedding model/version, vector, and one or more role weights. The role list is derived from the stored ontology rather than hard-coded in the upload form. The current seed contains 21 roles: SDE, ML Engineer, AI Engineer, Frontend Developer, Mobile App Developer, Data Analyst, Site Reliability Engineer, Blockchain Developer, Game Developer, UI/UX Designer, Network Engineer, Database Administrator, Business Analyst, Backend Developer, Cloud Engineer, Cybersecurity Analyst, Data Engineer, Data Scientist, DevOps Engineer, Full-Stack Developer, and QA/Test Engineer.

9.2 Candidate Vector Cache

Candidate skill vectors are generated in batches and cached on the extracted profile together with the configured embedding model and version. Analysis reuses a compatible cache and re-embeds only when the cache is missing or the model/version changes. Stored ontology vectors are checked for model/version and dimension compatibility before scoring.

9.3 Deterministic Formula

score = round(100 x sum(weight_i x match_i) / sum(weight_i))

Each role skill receives a normalized match value. Explicit canonical names and safe aliases are considered first, and category gates prevent unrelated categories from satisfying one another. Candidate evidence and proficiency can cap a match when the supporting signal is weak.

CategoryThresholdMeaning
Strong80% or aboveSkill is strongly aligned with the role requirement.
Developing60% to 79%Skill is present but needs depth, evidence, or practice.
GapBelow 60%Skill should be considered for the prioritized roadmap.

9.4 Gap Priority

Gap priority is calculated from role importance and missing strength: raw = weight x (1 - match). The raw values are normalized by the largest gap so the highest-impact missing skill receives priority 1.0. This provides a ranking without pretending that every gap has identical urgency.

const raw = gap.weight * (1 - gap.m); priority = raw / maxRaw; study_plan = gaps.sort((a, b) => b.priority - a.priority);

11 / Assistant

Grounded AI Assistant

11.1 Context Boundary

The Assistant is not a general chatbot with unrestricted access to the database. The backend first loads the student's latest completed owned report and constructs a constrained context containing the target role, scores, demonstrated skills, gaps, evidence summaries, and study plan. The user's message is then sent to the configured text provider with grounding instructions.

11.2 Allowed Questions

  • Which gap should I learn first?
  • Why is my readiness score low?
  • What project can I build to practice this gap?
  • Which skills are already supported by my evidence?
  • How should I prepare for the selected role?

11.3 Guardrails

  • Do not invent skills, projects, experience, certifications, or scores.
  • Do not claim that unrelated technologies satisfy a requirement.
  • Do not expose another student's analysis or private resume text.
  • If no completed analysis exists, direct the student to New Analysis.
  • Return a controlled error when provider configuration is unavailable.
Interpretation: the Assistant explains stored analysis; it does not replace the deterministic scoring layer or human evaluation.

16.10 Operational Boundaries

  • Vercel temporary filesystem storage is not durable; persistent resume storage should be moved to object storage for production.
  • Free-tier AI providers have quotas and transient overload; provider errors are mapped to controlled API responses.
  • Cold starts and external provider latency mean a first request can be slower than a warm request.
  • Atlas Network Access and demo credentials must be hardened before any non-academic use.

18 / Evaluation

Security, Limitations, and Future Work

18.1 Current Limitations

  • Readiness scores are guidance signals, not proof of ability or a guarantee of employment.
  • Public GitHub and LeetCode data can be unavailable, stale, rate-limited, or incomplete.
  • AI output quality depends on provider availability, prompt constraints, and source evidence quality.
  • Vercel temporary storage is not a durable long-term resume store.
  • Free-tier provider quotas and serverless cold starts can increase response time.
  • Current application review is a workflow tool, not a replacement for human hiring decisions.

18.2 Future Enhancements

  1. Move resume files to durable object storage with signed, time-limited download URLs.
  2. Add background job infrastructure for resilient analysis retries and larger workloads.
  3. Add model drift dashboards and scheduled ontology/resource refresh audits.
  4. Support institution-level placement analytics with privacy-preserving aggregation.
  5. Add calendar-based study scheduling, reminders, and milestone analytics.
  6. Add richer interview preparation linked to verified gaps and application role.
  7. Introduce automated CI for tests, lint, build, dependency audits, and deployment previews.
  8. Improve internationalization, accessibility audits, and screen-reader regression coverage.

18.3 Responsible AI Position

Responsible use: Vortex should help a student understand and act on evidence. It should not fabricate achievements, rank people as objectively employable, expose private data, or replace a qualified human decision-maker.

19 / Conclusion

Conclusion and Viva Summary

Vortex demonstrates how a conventional job board can be extended into an evidence-based preparation system. Its value comes from the connection between the application lifecycle and the learning lifecycle: a student can discover a role, apply, inspect readiness for that role, follow a roadmap, and receive grounded guidance without leaving the same workspace.

The implementation keeps responsibilities separated. React presents the workflow, Express protects and coordinates it, MongoDB stores durable state, Groq structures and explains text, Gemini provides pinned vector representations, and deterministic application code controls scoring, thresholds, ownership, and verified resources. This design makes the system suitable for academic demonstration while also exposing clear paths for production hardening.

Jobs + Evidence + Role Ontology + Deterministic Scoring + Grounded Guidance = Actionable Career Preparation

One-sentence Explanation

Vortex stores job postings and candidate profiles, extracts evidence-based technical skills from resumes and public coding profiles, compares them with role requirements, calculates readiness, identifies skill gaps, and provides personalized preparation through a verified study roadmap and grounded AI Assistant.
